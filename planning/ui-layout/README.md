# WinForms UI layout extraction

Generated by `scripts/extract-winforms-layout.py`. This is **extracted upstream
layout data only** — it describes what ShareX v21.0.0's WinForms designer
files declare. It is **not** evidence that any of this layout is implemented
in the macOS port. Cross-reference against `planning/feature-ledger.json`
before claiming a form is built.

## Commands

```sh
python3 scripts/extract-winforms-layout.py --all --source reference/ShareX --out-dir planning/ui-layout
python3 scripts/extract-winforms-layout.py --designer reference/ShareX/ShareX/Forms/MainForm.Designer.cs --out <file>
```

## What the extractor covers

For every `*.Designer.cs` under `reference/ShareX`, paired with its
invariant/English `.resx` (the file with no culture suffix, if one exists),
the extractor parses the `InitializeComponent()` method body statement by
statement and produces, per form:

- `controls[]`: name, type (declared field type preferred over the
  instantiation type), `parent` / `parent_slot` / `child_index` recovered
  from `Controls.Add(...)`, `<Slot>.AddRange(new T[] { ... })` (covers
  `Items`, `DropDownItems`, `Columns`, and any other collection-add call),
  and split-container `Panel1`/`Panel2` slots; every simple property
  assignment it can see (`Location`, `Size`, `Text`, `Anchor`, `Dock`,
  `TabIndex`, `Font`, colors, `Padding`/`Margin`, `Minimum`/`Maximum`/`Value`
  decimals decoded to real numbers, etc.); and a `resources[]` list tying
  properties back to `.resx` keys, covering both the classic
  `resources.GetString(...)`/`GetObject(...)` call style and the modern
  `resources.ApplyResources(control, "key")` bulk style used by most ShareX
  forms (all matching `key.*` resx entries are resolved and folded into that
  control's `properties`).
- `tree`: a nested structure rooted at the form, with a `slots` map per node
  (e.g. `Controls`, `Panel1.Controls`, `Items`, `DropDownItems`) whose
  children are ordered by source add-order — this is the real
  parent/child hierarchy, not designer field-declaration order.
- `strings`: every non-typed (plain string) `.resx` entry, keyed by resource
  key, for the invariant culture.
- `binary_resources`: keys/mimetypes of any binary/base64 resx entries
  (icons, images), value bytes skipped. **None were found anywhere in the
  ShareX source tree** — this codebase does not embed icons/bitmaps in
  per-form `.resx` files, so this array is empty in every generated JSON.
  Icon/image assets live elsewhere and are out of scope for this tool.
- Form metadata: `base_class` (from the sibling non-Designer `.cs` file's
  `partial class X : Y` declaration), `client_size`, `text`,
  `auto_scale_dimensions`, `auto_scale_mode`, `menu_strip`, and `tab_order`
  (derived from `TabIndex` values, from both code and resx-resolved sources).
- `parse_coverage`, `total_statements`, `parsed_statements`, and
  `unparsed_lines` (line number + raw text) — nothing is ever silently
  dropped; unrecognized statements are always visible in the JSON.

`--all` also writes `index.json`: one row per form with project, control
count, coverage, and output path.

## Aggregate coverage

**104 form JSON files** written. **Aggregate parse coverage: 1.0000**
(14,902 / 14,902 statements recognized across all forms). Every individual
form also reports `parse_coverage = 1.0`.

Caveats behind that number, so it isn't read as "100% perfect extraction":

- **8 of the 104 files are not UI forms.** `Properties/Resources.Designer.cs`
  in each project (`ShareX`, `ShareX.HelpersLib`, `ShareX.UploadersLib`,
  `ShareX.ScreenCaptureLib`, `ShareX.MediaLib`, `ShareX.ImageEffectsLib`,
  `ShareX.HistoryLib`, `ShareX.IndexerLib`) is the auto-generated strongly
  typed resource accessor class, not a WinForms designer file. It has no
  `InitializeComponent()`, so it's reported with 0 controls, 0 statements,
  and coverage trivially 1.0 (defined that way when there is nothing to
  parse) plus one `unparsed_lines` note explaining why. They were left in
  `index.json` rather than silently excluded, per "do not silently drop
  anything."
- **"Coverage" measures statement recognition, not full literal
  structuring.** Every statement in every `InitializeComponent()` was
  classified into a known shape (property assign, `Controls.Add`,
  `AddRange`, instantiation, event wiring, `ApplyResources`, etc.), so
  nothing landed in `unparsed_lines`. But roughly **5.6% of individual
  property values** (838 of 15,013 across all forms) are complex C#
  expressions the value-parser doesn't structurally decode — `Color`,
  `Cursor`, enum member references, inline `Font` construction — and are
  preserved verbatim as `{"kind": "expr", "raw": "<original C# text>"}`
  rather than a typed value. `Location`/`Size`/`Point`/`Padding`/decimal
  `Minimum`/`Maximum`/`Value` are structurally decoded; most enums and color
  expressions are not, by design (never crash, never guess a value from an
  unfamiliar expression shape).
- **48 controls across all forms have `parent: null`** (of 2,349 total).
  Spot-checked: the large majority are legitimately parentless WinForms
  component-tray objects that are never added via `Controls.Add` —
  `ContextMenuStrip` (26), `ToolTip` (11), `NotifyIcon` (3), `ImageList` (3),
  `Timer` (2) are assigned to other controls' properties (e.g.
  `x.ContextMenuStrip = cmsFoo;`), not parented in the control tree. A
  handful (`txtRapidSharePremiumUserName`, `btnCopyShowFiles`,
  `actRapidShareAccountType` in `UploadersConfigForm`) are genuinely dead
  designer fields in the upstream source itself — declared and configured
  but never added to any container's `Controls` anywhere in the file. This
  was verified by reading the source, not inferred; it is upstream reality,
  not a parser gap.

No form is below the 0.95 coverage bar — all are at 1.0 statement coverage,
so there is no "worst forms" ranking by that metric. The nuance above is the
honest picture instead.

## MainForm verification

`reference/ShareX/ShareX/Forms/MainForm.Designer.cs` (2415 lines,
`ShareX__MainForm.json`): **parse_coverage = 1.0** (1310/1310 statements),
266 controls, 0 unparsed lines.

Spot-checked against the source by hand. Top-level `Controls` slot on the
form, in add-order: `pMain`, `pToolbars`. The tree correctly nests:

- `pMain` → `Controls`: `pHotkeys` (→ `dgvHotkeys` with its `Columns`),
  `ucTaskThumbnailView`, `scMain` (a `SplitContainerCustomSplitter`) →
  `Panel1.Controls`: `lvUploads` (the task list view, with its 7
  `ColumnHeader`s under `Columns`) and `Panel2.Controls`: `pbPreview`.
- `pToolbars` → `Controls`: `tsMain` (the `ToolStripBorderRight` actions
  toolbar) → `Items`: `tsddbCapture`, `tsddbUpload`, `tsddbWorkflows`,
  `tsddbTools`, ..., each with its own `DropDownItems` correctly nested one
  level deeper (e.g. `tsddbCapture.DropDownItems` = `tsmiFullscreen`,
  `tsmiWindow`, `tsmiMonitor`, ...).

Note: this MainForm does not use a classic `MenuStrip` or `StatusStrip`
control — there is no `MainMenuStrip` assignment and no `StatusStrip` type
declared anywhere in the file (confirmed by direct search). Its "menu" is
`tsMain`, a vertical action toolbar, plus two standalone `ContextMenuStrip`s
(`cmsTaskInfo` for the task list, `cmsTray` for the tray icon) that are
correctly extracted but — like all context menus — appear with
`parent: null` since they attach via a `ContextMenuStrip` property, not
`Controls.Add`. `menu_strip` and `text` are both `null` for MainForm because
neither is set in the designer file (the window title is set at runtime in
code-behind, not hardcoded).

## Known limitations

- Controls added to their parent in the non-designer `.cs` code-behind
  (rather than in `InitializeComponent()`) will not show a parent here —
  this tool only reads the designer file.
- `ColumnStyles`/`RowStyles` for `TableLayoutPanel` are supported if present
  as `.Add(...)` calls, but no form in this codebase configures them that
  way (all rely on designer defaults), so none are populated.
- Localized (non-invariant) `.resx` files (e.g. `*.fr-FR.resx`) are not
  read; only the invariant/English resx is resolved.
